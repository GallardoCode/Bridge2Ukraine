# Payload CMS prototype for Bridge2Ukraine

> **Prototype.** This folder explores running the Bridge2Ukraine site from
> [Payload CMS](https://payloadcms.com). It lives on the `prototype/payload-cms`
> branch. The static site in the repository root is untouched and still what
> GitHub Pages serves.

The same four pages (home, donate, donate items, volunteer) are rendered by
Next.js from content stored in Payload. The markup and CSS are the original
ones, so the pages look the same: a screenshot diff against the static site
differs by under 40 pixels per page.

In the admin you can:

- edit every text, image, button and stat on the four pages
- add, remove, reorder and reuse page sections (12 block types)
- manage stories and partner logos in their own lists and pick them into pages
- save drafts, preview them live next to the editor, then publish

More detail: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) (how it fits together,
trade-offs) and [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md) (Docker, Plesk, CI,
migrations, backups, rollback).

## Local development

You need Node 24 (`.nvmrc`), pnpm 10 (`corepack enable pnpm`) and Docker.

```bash
cd payload-poc
cp .env.example .env
pnpm install
pnpm db:up        # Postgres 18 in Docker on localhost:5433
pnpm seed         # imports the static site's content and photos
pnpm dev          # http://localhost:3000
```

Log in at http://localhost:3000/admin as `dev@example.com` / `dev-password`.
The seed creates that account only in development.

The app runs on your machine with hot reload; only Postgres runs in Docker.
Code changes never need an image rebuild. If you change a collection or block
definition and the admin still shows the old fields, restart `pnpm dev`.

### Things to try

1. Open **Pages → Home**. Drag the "Mission statement" block below "Stories
   mosaic", and watch the preview pane on the right update.
2. Click **Add Layout** and add a block from another page, for example a
   "Button row".
3. Edit a story under **Library → Stories**. Every page that uses it changes.
4. Make an edit and leave it unpublished. http://localhost:3000 in a private
   window still shows the published version.

## Commands

| Command | What it does |
| --- | --- |
| `pnpm dev` | Next.js dev server with the site and the admin. Syncs the DB schema from the config (push mode). |
| `pnpm db:up` / `db:down` / `db:reset` | Start, stop, or wipe and restart the dev Postgres. |
| `pnpm seed` | Deletes pages, stories and partners, then re-imports them from the static site. |
| `pnpm migrate:create <name>` | Writes a migration for config changes. Review the SQL and commit it. |
| `pnpm migrate:check` | Fails if the config changed without a migration (runs in CI). |
| `pnpm test` | Integration tests against the `bridge2ukraine_test` database. |
| `pnpm lint` / `pnpm typecheck` | ESLint and TypeScript. |
| `pnpm generate:types` | Regenerates `src/payload-types.ts`. `pnpm dev` also does this. |
| `pnpm content:export` | Builds a content bundle for the first production deploy. See DEPLOYMENT.md. |

## Layout

```text
payload-poc/
  src/
    payload.config.ts        Payload config: collections, globals, Postgres, migrations
    collections/             Pages, Stories, Partners, Media, Users
    globals/SiteSettings.ts  logo, brand name, footer contacts
    blocks/config.ts         the 12 page-section blocks
    components/blocks/       React for each block, using the original CSS classes
    app/(frontend)/          the public site, draft preview routes, /healthz
    app/(payload)/           the admin and REST/GraphQL API (generated by Payload)
    migrations/              committed SQL migrations
    seed/                    imports the static site
  tests/                     integration tests (Vitest + real Postgres)
  deploy/                    production compose file and deploy/backup/restore scripts
  scripts/                   migration drift check, content export
  Dockerfile                 production image
  compose.dev.yml            dev Postgres
```

The CI workflow lives at the repository root in
`.github/workflows/payload-poc.yml`, because GitHub only reads workflows from
there.
